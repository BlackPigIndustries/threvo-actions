# Stripe host conformance

The Stripe host exercise tests the adopter's repository and transaction design
without prescribing its schema. It complements the generic action-store checks:
the action store controls proposal lifecycle, while the Stripe host repository
owns stable business intent and exclusion of conflicting resource writers.

## Driver contract

Implement `StripeHostConformanceDriver` in the adopter's test suite. The driver
declares one action group and runs each `StripeHostScenario` against fresh,
isolated fixtures in the adopter's actual repository implementation.

```python
from threvo_actions.integrations.stripe import (
    StripeHostActionGroup,
    StripeHostCapabilities,
    StripeHostConformanceDescriptor,
    StripeHostScenario,
    StripeHostScenarioResult,
    StripeHostScenarioDisposition,
    assert_stripe_host_conforms,
)


class RefundHostDriver:
    @property
    def descriptor(self) -> StripeHostConformanceDescriptor:
        return StripeHostConformanceDescriptor(
            action_group=StripeHostActionGroup.REFUNDS,
            profile_identifier="my-app:postgres-refunds:v1",
            capabilities=StripeHostCapabilities(
                independent_connections=True,
                normal_application_writer=True,
                lost_acknowledgement_injection=True,
            ),
        )

    async def run_scenario(
        self, scenario: StripeHostScenario
    ) -> StripeHostScenarioResult:
        await self.exercise_real_repository(scenario)
        return StripeHostScenarioResult(
            scenario=scenario,
            disposition=StripeHostScenarioDisposition.PASSED,
        )


report = await assert_stripe_host_conforms(RefundHostDriver())
```

Returning `PASSED` is a test assertion, not an attestation generated by the
library. `exercise_real_repository` must fail before returning unless the named
postconditions below were observed. Keep scenario fixtures independent so one
durable claim cannot make a later race pass accidentally.

## Required scenarios

| Scenario | Required observation |
| --- | --- |
| `immutable_intent` | Repeating `remember` with the exact snapshot and requester succeeds; changing either for the same tenant and intent is rejected. |
| `tenant_isolation` | A different tenant cannot load, rebind, close or record an outcome for the intent. |
| `same_effect_race` | Two separately created connections race one effect; only one unresolved owner remains and neither result permits two submissions. |
| `conflicting_resource_race` | Distinct intents that affect one payment/subscription/invoice cannot both acquire the resource. |
| `unrelated_resource_progress` | An operation for another resource proceeds while the first resource is claimed. |
| `normal_writer_exclusion` | The application's ordinary writer cannot change, delete or reparent the reserved resource through its normal mutation path. |
| `lost_reservation_acknowledgement` | Inject loss after the reservation commit; the call is uncertain and the durable claim remains. It must not return a definite refusal or safe acquisition. |
| `expired_admission` | A lock wait that passes `not_after` cannot acquire and dispatch. |
| `closed_intent_non_reopening` | Known no-submission and terminal outcome close the attempt without making its stable intent reusable for a different request. |
| `outcome_idempotence` | Retrying the exact terminal outcome after an application/runtime failure succeeds without duplicating the effect; a different outcome is rejected. |
| `delayed_closure_owner_safety` | A delayed close for an older intent cannot release or overwrite the current resource owner. |
| `diagnostic_minimization` | Reports and thrown errors contain no seeded API key, provider ID, protected snapshot, connection string or private payload. |

`independent_connections`, `normal_application_writer` and
`lost_acknowledgement_injection` are required capabilities in v1. Setting one
to false or returning `NOT_EXERCISED` fails the runner. A refund report applies
only to refunds. Repeat the exercise with the subscription and credit-note
drivers before claiming conformance for those groups.

## Fixture rules

- Use two independently acquired database connections or sessions backed by
  the same database. Two wrapper objects around one transaction do not qualify.
- Exercise the same credential and SQL path used by the normal application
  writer. A privileged migration/admin connection cannot prove writer
  exclusion.
- Inject acknowledgement loss after a real commit boundary. Raising before the
  write proves nothing about uncertainty.
- Use a controllable clock or lock holder for the deadline case.
- Seed recognizable secrets and scan fixture logs, exceptions and the returned
  report without printing the secret value in assertion messages.
- Run against migrations from an empty database and the supported upgrade
  path. Constructors must never migrate automatically.

Driver exception messages are intentionally discarded by
`assert_stripe_host_conforms`; the public error contains only the scenario and
stable disposition. Keep detailed database diagnostics inside the adopter's
secured test environment.
