# `0.3.1` release record

This patch release corrects the runtime and packaging issues found during the
independent review of `0.3.0`. It preserves the `0.3.x` public action contracts,
stored proposal and receipt shapes, action identities, and database schemas.

## Migration from `0.3.0`

1. Upgrade the exact pin with `uv add "threvo-actions==0.3.1"`, or install the
   Stripe SDK transport with `uv add "threvo-actions[stripe]==0.3.1"`.
2. Custom Stripe gateway implementations now work with the base package. The
   Stripe SDK is loaded only when a caller supplies an SDK client or imports an
   SDK gateway explicitly. Existing documented imports remain valid.
3. Pass `clock`, `identifiers`, `event_sink`, `retention_store`, or
   `runtime_revision` to `StripeActions` when the host needs deterministic time,
   lifecycle telemetry, custom identifiers, retention, or provenance. All
   configured action groups share the resulting runtime and clock.
4. Treat `stripe_refund_pending` as `PROVISIONAL_ABSENCE`. It means Stripe
   authoritatively returned an unsettled refund, rather than that the provider
   query was unavailable.
5. A proposal that loses execution admission to an actively executing proposal
   now returns `IN_PROGRESS`. Terminal or otherwise inactive conflicts retain
   the existing replay result.

No data migration is required. Hosts that replaced an operation group's public
`runtime` attribute can continue to do so, although constructor injection is now
the documented configuration path.

## Deadline and authorization semantics

Authority and proposal expiry are checked after live authorization work. The
execution recovery lease begins when durable admission succeeds, so time spent
inside live authorization consumes authority validity but does not shorten the
post-admission recovery lease. Stripe workflows use the same injected clock as
the runtime, which makes these boundaries deterministic in host tests.

Authorization denial before a proposal can be disclosed continues to raise
`ProposalNotFoundError`; this intentionally avoids revealing whether a scoped
proposal exists. Failures after a visible proposal enters the lifecycle are
returned and persisted as typed outcomes.

## Qualification and publication

The full local suite, strict Ruff formatting and linting, strict mypy, Bandit,
dependency audit, documentation build, source and wheel verification, and clean
installed-artifact checks gate the release candidate. CI repeats qualification
on Python 3.11 through 3.13 and across the supported optional integrations and
database adapters.

Publication uses one CI-built candidate promoted unchanged through TestPyPI and
PyPI, with signed-tag and artifact-digest verification. Independent adoption
evidence remains pending. On 12/09/2026 the repository owner explicitly
authorized a one-time `v0.3.1` publication exception with
`skip_adoption_gate=true`; all technical, provenance, signed-tag, TestPyPI and
PyPI verification gates remain mandatory.
