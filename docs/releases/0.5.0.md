# 0.5.0 release record

This minor release adds a reusable operator-recovery boundary for actions whose
provider outcome remains pending or unresolved. A trusted host can record a
bounded intervention and resume authoritative verification without reopening
execution. The release also extends the experimental `internal/v0` receipt
union with a closed `recovery` discriminator.

## Migration from 0.4.3

1. Stop every runtime and retention writer that uses the action store.
2. Upgrade the exact pin:

       uv add "threvo-actions==0.5.0"

3. Apply the contract migration for each configured adapter while writers remain
   stopped:

       uv run threvo-actions postgres migrate --dsn-env DATABASE_URL --schema threvo_actions --writers-quiesced
       uv run threvo-actions mysql migrate --dsn-env DATABASE_URL --writers-quiesced
       uv run threvo-actions sqlite migrate --database actions.sqlite3 --writers-quiesced

4. Start the 0.5.0 writers only after migration inspection reports no pending
   versions.
5. If the application persists or exchanges receipt JSON, update every closed
   union to accept `receipt_type="recovery"`,
   `status="verification_resumed"`, and a `recovery_operator` participant
   before enabling operator recovery.

Fresh databases apply the complete schema without a quiescence declaration.
Existing PostgreSQL schema version 4 advances to 5, MySQL version 2 advances to
3, and SQLite version 1 advances to 2. Applied migration files remain
checksummed and immutable.

## Operator contract

The host authenticates and authorizes `RecoveryOperator`; the library does not
provide an identity system. `operator.reference` and `intervention_reference`
must be pseudonymous bounded references. The host retains the referenced case,
bounds retry access, and passes the exact observed proposal revision.

`resume_verification` accepts only `verification_pending` and
`verification_unresolved`. It records a recovery receipt causally linked to an
earlier receipt, resets the verification attempt budget, and immediately calls
the verifier. It never calls the executor. A stale revision returns conflict;
a terminal proposal is not reopened.

## Stabilization and release authorization

Threvo is the maintainer-owned pilot that exposed the need for this generic
boundary. It does not count as independent adoption, and the feature-release
hold remains active after publication.

The repository owner explicitly directed the complete Threvo integration and
permitted reusable library additions on 2026-09-13. The release workflow's
default-off exception is bound to `v0.5.0`; it cannot authorize a later release
and does not bypass candidate qualification, signed-tag verification, artifact
identity, TestPyPI/PyPI verification, or protected environments.

## Qualification

The candidate must pass Ruff, formatting, strict mypy, the full suite, Bandit,
dependency audit, strict documentation build, and artifact verification on
Python 3.11 through 3.13. PostgreSQL integration tests must apply migration 5
and exercise the resumed lifecycle. SQLite must prove an existing version-1
store refuses migration without writer quiescence. MySQL CI must validate the
new receipt through both stored JSON validation paths.
