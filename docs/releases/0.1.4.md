# `0.1.4` release record

Status: **candidate implementation complete; independent DX and protected
publication gates pending**

`0.1.4` adds an experimental gradual-reveal authoring namespace without
changing the supported expert runtime, lifecycle vocabulary, serialized
records, or database migrations.

## Candidate contents

- Strict/frozen `ActionSpec` declarations and explicit typed registration.
- Frozen `ActionApplication` catalogs with operation-scoped host dependency
  binding and invalidated post-scope facades.
- Static allowlisted inspection that invokes no recipes or live resources.
- Dependency-scoped Pydantic AI prepare/resume with unchanged fixed-runtime
  compatibility.
- Migrated reference applications and a 68-line executable tour.

## Compatibility

The namespace remains outside `threvo_actions.__all__` and follows the 120-day
support, revision, retirement, and stable-promotion policy in
[Versioning](../versioning.md). The expert imports remain the supported `0.1.x`
contract. This release adds no lifecycle state and no store migration.

## Promotion gates

- [x] Focused implementation, conformance, typing, leakage, and Pydantic AI
  tests pass locally.
- [ ] A workflow-dispatched candidate from the final source commit passes the
  full Python 3.11-3.13 and supported Pydantic matrix.
- [ ] The private, commit-addressed backend migration patch is validated
  against the exact candidate wheel.
- [ ] Expert baseline and every independent-human candidate attempt are
  recorded in the hash-linked adoption ledger and meet the absolute gates.
- [ ] A signed `v0.1.4` tag points to the recorded candidate source commit.
- [ ] The protected workflow promotes the same wheel and source distribution
  through TestPyPI and PyPI, and both index downloads match the candidate
  digests.

Unchecked gates are blockers, not deferred claims. No tag or public artifact
should be created from a rebuilt or rebased candidate.

The candidate and promotion are separate manual dispatches. The promotion run
downloads `release-distributions` from the recorded candidate run, verifies the
signed tag and candidate JSON, verifies the supplied SHA-256 of the complete
current adoption-record file, requires its single candidate-bound promotion
marker, verifies artifact digests, and never invokes the build backend. The
protected release-review approver reviews the ledger entries and their linked
digests; workflow automation does not parse or recompute the internal
entry-digest chain.
