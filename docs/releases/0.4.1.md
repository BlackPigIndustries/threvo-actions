# 0.4.1 release record

This corrective patch makes the Stripe host qualification boundary honest,
completes the gradual-reveal operations introduced in 0.4.0, packages the
approval request reference, and clarifies why the library exists. It adds no
Stripe action or connector.

## Migration from 0.4.0

1. Upgrade the exact pin with:

       uv add "threvo-actions==0.4.1"

2. Existing action definitions, Stripe facades, stored proposals, receipts,
   runtime transitions, and provider correlations remain compatible.
3. Replace assert_stripe_host_conforms with assert_stripe_host_exercise for
   qualification. The new adapter exposes primitive operations and cannot
   return passed. The library invokes and evaluates the twelve scenarios.
4. Legacy assert_stripe_host_conforms calls remain valid and emit a
   DeprecationWarning. Their report adds assessment_basis=driver_attestation and
   conformance_established=false. The passed property means only that all
   driver claims said passed.
5. BoundAction now forwards read_recovery, export_evidence, and
   observation_context.
6. Approval request users may import the records and PostgreSQL store from
   threvo_actions.integrations.approval_channels. Apply its migration
   explicitly; constructors never migrate.
7. ActionRecoveryView is an additive package-root export. The evidence bundle,
   validation report, validator, and renderer are discoverable from
   threvo_actions.experimental while their external contract is evaluated.
8. PostgreSQL hosts that coordinate ordinary writers with the Stripe ledger
   should derive the advisory-lock text using
   stripe_resource_lock_reference. The 0.4.0 NUL-delimited value was rejected
   by PostgreSQL before the lock could be acquired.

The reference host also reconstructs strict Decimal-bearing snapshots through
Pydantic's JSON validation boundary, and approval evidence may now use a shorter
authority lifetime within its immutable request window.

## Evidence document status

The threvo.actions.evidence/v1 JSON shape remains experimental. Callers must pin
the exact library version when persisting or exchanging it and must review its
migration notes before upgrading. Its models remain strict, frozen Pydantic
models, but immutability of one instance does not imply cross-release schema
stability. Promotion requires the outside-adoption and post-adoption evidence
defined in docs/versioning.md.

The evidence bundle remains an unsigned_host_projection. Its digest validates
internal consistency and does not authenticate the exporter or prove
completeness, legal sufficiency, or compliance.

## Qualification meaning

The 0.4.0 stripe-host-conformance/v1 format is a driver attestation. It cannot
establish that a repository was touched. It must not be used as deployment or
customer conformance evidence.

The new stripe-host-exercise/v1 runner owns scenario order, concurrent calls,
an interleaved ordinary-writer race, deadlines, fault-injection requests, and
assertions. Its adapter still defines
which application operations are exercised. Reviewers must confirm that those
primitives reach the real repository, use independent connections, cover an
ordinary writer, and inject acknowledgement loss after durability.

## Adoption and release hold

No consenting outside application completed the adoption protocol for this
patch. Reference applications, CI databases, and maintainer-controlled tests do
not satisfy that gate. The project enters the documented 0.4 feature-release
hold after this corrective release. New connectors, actions, and public
authoring abstractions remain ineligible for publication until the evidence
conditions in docs/stabilization.md pass.

The repository owner explicitly directed publication of this corrective 0.4.1
release on 12/09/2026. The exact one-time promotion exception does not create
adoption evidence and cannot authorize a later release. Candidate qualification,
signed-tag verification, artifact identity, protected environment review,
TestPyPI verification, and PyPI verification remain mandatory.

## Qualification

The candidate must pass Ruff, formatting, strict mypy, the full test suite,
Bandit, dependency audit, strict documentation build, build verification, and
immutable-wheel checks on Python 3.11 through 3.13. PostgreSQL CI exercises the
packaged Stripe and approval migrations. Publication promotes the exact
qualified candidate bytes through TestPyPI and PyPI before creating the GitHub
release.
