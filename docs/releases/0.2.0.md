# `0.2.0` release record

This minor release adds the optional Stripe connector and a standalone sandbox
refund application, and corrects three runtime/adapter boundary failures.
Published artifacts are qualified through the signed candidate/promotion
workflow; a source record is not evidence of publication.

## Migration from `0.1.6`

1. Pin the exact new package with uv and run your host conformance tests.
2. A terminal `VerificationResult` may no longer contain `FAILED_UNKNOWN`
   items. Continue verification using a nonterminal result, or report only
   outcomes that are authoritatively settled.
3. Slow authorization or admission can now refuse a previously accepted
   execution. If admission already committed, expiry is recorded as a known
   no-effect failure; the executor is not invoked. Hosts must still guard their
   own final mutation boundary and define realistic leases/timeouts.
4. SQLite cancellation now waits for a background operation to finish before
   propagating. A caller can take up to the configured lock/operation duration
   to observe cancellation. Custom stores must likewise settle background
   writes before allowing runtime compensation.
5. No existing library schema or serialized proposal/receipt migration is
   required. Stripe remains optional; importing `threvo_actions` does not load
   its SDK. The new app's schema belongs to that host, separately from library
   migrations.

The experimental authoring namespace retains its existing support window and
equivalence-test obligations. No public payment protocol, compliance guarantee,
or Visa/Mastercard interoperability is introduced.

## Stripe qualification scope

Tested against Stripe Python 14.4.1 using provider-shaped fixtures and a real
Stripe sandbox refund. The database-backed application scenarios cover tenant
separation, independent approval, restart recovery, competing proposals,
ambiguous acceptance, no resend after a stale reservation, drift and late
failure. The assistant is tested with Pydantic AI `FunctionModel`, with external
model requests disabled. Real model-provider output is not release evidence.

The reference app rejects live credentials. Static bearer identities and its
local master-key configuration are reference host choices, not a qualified
production identity/key deployment. Direct Connect account headers are tested
at the SDK boundary; a real connected-account sandbox flow remains a next step.

## Adoption evidence

The repository owner requested this release together with the fixes and Stripe
application on 08/09/2026. Independent external adoption remains pending. The
release workflow's explicit `v0.2.0`-only owner exception permits publication
without relabeling internal tests or sandbox qualification as external adoption.
All technical qualification, artifact provenance, signed tag, TestPyPI and PyPI
promotion requirements remain in place.
