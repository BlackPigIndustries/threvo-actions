# `0.4.0` release record

This minor release turns the existing Stripe action groups into a progressively
adoptable host integration. It adds typed composition, reusable PostgreSQL host
bookkeeping, executable conformance, actionable recovery, minimized evidence
exports, billing scenarios, sandbox qualification runners, and a server-bound
approval-channel reference recipe.

## Migration from `0.3.2`

1. Upgrade the exact pin with `uv add "threvo-actions==0.4.0"`, or install the
   Stripe SDK transport with `uv add "threvo-actions[stripe]==0.4.0"`.
2. Existing `StripeActions(...)` calls, root exports, action identities,
   request/result models, receipt JSON, stored runtime proposals, and core
   database migrations remain compatible.
3. Applications may adopt `StripeServices`, scenario factories, recovery
   views, evidence exports, and due-work discovery independently. Evidence
   models and validators are imported from `threvo_actions.evidence`; they do
   not expand the frozen package-root namespace.
4. The optional Stripe host ledger is a new, separately checksummed
   `threvo_stripe` schema. Inspect and apply it explicitly with
   `migrate_stripe_postgres`; constructors never migrate. Application-owned
   approval, recovery-case, and reference business tables remain outside the
   package migration.
5. Before enabling provider mutations, choose the host customer-resource
   boundary, inventory every ordinary writer, enforce the writer guard, run the
   host conformance exercise, and configure the recovery worker. Existing
   pending proposals do not need rewriting.

## Scope and evidence

Refunds, period-end subscription cancellation scheduling and withdrawal,
open-invoice reductions, and paid-invoice customer-balance credits retain their
`0.3.2` completion predicates and limitations. Recovery views explain safe next
steps and sibling effect ownership. Post-terminal provider observations remain
separately attributed host case evidence and never rewrite runtime receipts.

Evidence exports are minimized `unsigned_host_projection` envelopes. Their
digest and validator establish internal consistency; they do not authenticate
the exporter, prove completeness, or establish legal or audit sufficiency.

Deterministic and installed-artifact qualification covers the supported Python
and optional-integration matrix. PostgreSQL and Stripe sandbox runners are
included, but this development host had no configured qualification database or
Stripe test credentials. Outside-host adoption also remains pending. Skipped or
absent external evidence is not represented as a passing result.

## Qualification and publication

The release candidate must pass Ruff, strict mypy, the full test suite, Bandit,
dependency audit, strict documentation build, distribution verification, and
installed-artifact checks on Python 3.11 through 3.13. Publication promotes one
CI-built candidate unchanged through TestPyPI and PyPI, with a verified signed
tag and artifact-digest checks at every boundary.

On 12/09/2026 the repository owner explicitly directed publication of this
release. The exact `v0.4.0` one-time exception uses
`skip_adoption_gate=true` because independent adoption evidence is pending. It
does not create adoption evidence or waive candidate qualification, provenance,
tag verification, protected environment review, TestPyPI verification, or PyPI
verification. It cannot authorize a later release.
