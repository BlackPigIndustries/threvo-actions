# 0.6.0 release record

0.6.0 consolidates what the first full application integration taught us. It
keeps the action lifecycle provider-neutral while moving repeated host mechanics
into reusable, typed components.

## Migration from 0.5.0

1. Pin the new minor and the integrations you use:

   ```bash
   uv add "threvo-actions==0.6.0"
   ```

2. Add `recovery_authorization` to every definition whose operators may call
   `resume_verification`. Recovery now fails closed when that port is absent.
   Authenticate the operator in the host and bind the authorization decision to
   the tenant, proposal, operator reference, intervention reference, and time.
3. Replace custom proposal identifier providers with
   `prepare(..., proposal_reference=host_reference)` when the host already owns
   a durable request identity.
4. Replace local lifecycle switch tables with `classify_lifecycle()`. Treat
   `verification_unresolved` and partial completion as `needs_attention` even
   though automatic processing is closed.
5. Choose store transaction ownership per effect. Internal mutations may use
   `CallerOwnedTransactionSource`; remote effects need independently committed
   lifecycle writes around the provider call.
6. PostgreSQL and SQLite action stores require no core schema migration from
   0.5.0. MySQL stores must apply packaged migration `004` with writers
   quiesced; it extends strict authority-evidence validation and the guarded
   append-only update routine for `external_attestation`. The local-KEK
   integration separately requires a host-owned wrapped-key store and migration
   if adopted.
7. If authority evidence is serialized outside an official store, allow the
   optional `external_attestation` member. It is a reference to host-verified
   evidence, not library signature verification.

## Compatibility

The 0.5.0 root API remains available. `ExternalAuthorityAttestation` is an
additive authority model. Host-owned proposal references add an optional keyword.
Recovery authorization intentionally changes a previously unsafe operation:
calling `resume_verification` without an explicit port now raises
`AuthorizationDeniedError` before any receipt, state transition, verifier, or
executor call.

`ActionOperationResult.is_terminal` is false for `verification_unresolved`
because authorized recovery can reopen verification. Use
`automatic_processing_closed` when deciding whether an unattended poller should
stop; it remains true for that state.

The installed PostgreSQL Stripe exercise is the same library-orchestrated
twelve-scenario contract previously shipped in the reference application. The
generic recovery worker preserves the earlier reference behavior and still
requires a host-owned durable lease schedule.

## Pilot evidence

The Threvo application runs the store/runtime conformance suites against its
actual PostgreSQL adapter and runs the installed Stripe host exercise against
its migrated ledger. It uses host-owned proposal references, explicit operator
authorization, exhaustive lifecycle projection, existing-tool Pydantic AI
bindings, and local-KEK envelope protection. Threvo is the maintainer-owned
pilot and does not count as independent adoption or external provider
qualification.

Publication still requires the repository release workflow: complete tests,
typing, lint, migration and installed-wheel checks; signed source tag; artifact
identity verification; TestPyPI byte verification; and PyPI promotion of those
same bytes.
